# معمارية الدمج — ما بقي وما تغيّر

## القرار المعماري

تم اعتماد مشروع الفريق بوصفه **Application Shell وOrchestrator**، واعتماد Brand‑DNA + Adaptive Memory بوصفهما **طبقة ذكاء قابلة للاستبدال والتدقيق**. لذلك لم نُنشئ pipeline ثانياً ولم نلغِ الوكلاء أو الواجهة.

## الـworkflow الثابت

```text
المستخدم/الشات
  → Orchestrator
  → Brand Agent
  → Strategy Agent
  → Product Agent
  → Idea Agent
  → إنتاج المحتوى والتصميم
  → التقييم
  → موافقة الإنسان
  → الجدولة
  → قياس الأداء
  → حلقة التعلم
```

التغيير داخل مرحلة «إنتاج المحتوى والتصميم» فقط:

```text
قديم: فكرة → مسودة نص واحدة → تصميم واحد → Review معطّل
جديد: فكرة → 3 مرشحين → تحقق/إصلاح → ترتيب → اختيار موصى به
      → تصميم → تقييم قبل/بعد التصميم → Review بشري
```

## المكونات التي بقيت كما هي

- FastAPI وSQLAlchemy وSQLite لبيانات التطبيق.
- React/Vite/Tailwind وواجهات البراند والمنتجات والحملات والشات.
- Orchestrator وتصنيف النية وتجميع الحقول الناقصة.
- Strategy Agent وProduct Agent وIdea Agent.
- مولد الصور وتركيب قالب البراند.
- صفحة اعتماد/رفض البوست والجدولة الناتجة عن الاعتماد.
- `post_id` وفكرة واحدة بوصفهما مصدر الاتساق بين النص والتصميم.
- ملف `docs/full_workflow.html` بوصفه المرجع المرئي المتفق عليه.

## ما استُبدل

| الجزء السابق | البديل المدمج | السبب |
|---|---|---|
| تحليل Brand Agent جديد عبر LLM كل حملة | ملف Brand DNA ثابت ومُصدّر ومُخزّن | ثبات الهوية وقابلية إعادة الإنتاج |
| مسودة محتوى واحدة | ثلاثة مرشحين بعقد Pydantic صارم | تنوع وفرصة اختيار وتحقق آلي |
| Prompt ثابت بلا نتائج تعلم | Prompt ثابت الهيكل + سياق سياسات active ديناميكي | الكود لا يعيد كتابة نفسه؛ السلوك يتحسن بالبيانات المعتمدة |
| Review يعيد null | بوابات بنيوية + هوية + نموذج/Cold Start + مراجعة بشرية | قرار واضح وتوقف آمن |
| جدولة 20:00 ثابتة في الكود | إعداد `DEFAULT_SCHEDULE_HOUR` | قابلية الضبط مع حفظ fallback |

## ما أُضيف

1. `brand_dna/`: preprocessing، نماذج Logistic Regression، SHAP، ranking، schema، repair.
2. `adaptive_memory/`: Evidence immutable، aggregation، validation، draft policies، activation.
3. `smart_social_contracts/`: سجل ملكية كل feature والـrole المسموح.
4. `services/brand_intelligence_service.py`: تهيئة الصفحة، فصل model/cold-start، تسجيل الأداء.
5. `services/campaign_intelligence.py`: نقطة التكامل الوحيدة للتوليد والتقييم والتصميم.
6. حقول trace في `GeneratedPost` وملخص ذكاء في `ContentPlan`.
7. جدول `PostPerformanceSnapshot` لنتائج 24h/72h وغيرها.
8. API للتهيئة والذاكرة والسياسات ونتائج الأداء.
9. شاشة «الذكاء والتعلّم» في React.
10. اختبارات، demo، preload، وفحص إصدار.

## ما لم يُحذف

لم نحذف وكلاء الفريق السابقين لأنهم ما زالوا مستخدمين في مسارات الاستراتيجية والمنتج والفكرة والتصميم المنفصل. أما وظائف المحتوى القديمة فبقيت للتوافق الخلفي، لكن مسار الحملات ومسار كتابة منشور من الشات يمران عبر طبقة المرشحين الموحدة.

## ترتيب السلطة

1. السلامة وسياسات المنصة.
2. Stable Brand DNA والقيود الصريحة.
3. Brief الذي وافق عليه المستخدم.
4. سياسات Adaptive Memory الفعالة والمطابقة للسياق.
5. الاختيارات الإبداعية.

لا تستطيع سياسة ذاكرة تجاوز forbidden words أو لون/موضع شعار إلزامي أو هدف الحملة. وكل سياسة ذاكرة soft افتراضياً.

## تخزين البيانات

يوجد مخزنان متعمدان:

- `marketing_os.db`: الكيانات التشغيلية للحساب والبراند والمنتج والحملة والمنشور والجدولة ونتائج الأداء.
- `outputs/adaptive_memory/app.db`: Evidence وInsights وPolicies، وهو مصدر الحقيقة التشغيلي للذاكرة.

الفصل يمنع خلط الهوية الثابتة بالتعلّم المتغير، ويسهّل استبدال backend الذاكرة لاحقاً دون تغيير التطبيق.

## مسار الصفحة الجديدة

```text
إدخال هوية يدوية
  → profile_type=stable_brand_identity
  → dna_status=cold_start
  → توليد 3 مرشحين
  → تحقق schema + brief + brand constraints
  → cold_start_quality_score فقط
  → موافقة إنسان
  → جمع نتائج حقيقية
  → بعد عينة كافية: تدريب نموذج خاص وتسجيله
  → dna_status=model_ready
```

لا يُستخدم نموذج Al Boraq لصفحة أخرى لمجرد أن المنتجات متشابهة.

## مسار الفشل

```text
استجابة LLM غير JSON/ناقصة/مخالفة
  → تسجيل الأخطاء
  → إعادة prompt مع repair feedback
  → بحد أقصى 3 محاولات
  → إن نجحت: تقييم وترتيب
  → إن فشلت: needs_review + لا اعتماد + لا جدولة
```

الـfallback ليس اختياراً صامتاً لمسودة مكسورة.
